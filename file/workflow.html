📋 Detailed Workflow & Technical Reference

Complete step-by-step technical documentation of how the Secure File Sharing System works — from key generation to file integrity verification.

// Algorithm Overview
AlgorithmRoleKey / Output SizeSecurity GoalWhy This Choice
SHA-512 File integrity fingerprint 512-bit hash (128 hex chars) Integrity detection Strongest SHA-2 variant. 2^512 collision space. No known practical attacks.
AES-GCM-256 File encryption (bulk data) 256-bit key · 96-bit IV · 128-bit auth tag Confidentiality + Authenticity Authenticated encryption. Fast, hardware-accelerated. GCM mode provides built-in tamper detection.
RSA-OAEP-2048 AES key wrapping 2048-bit modulus · SHA-256 hash Asymmetric key exchange Enables sender to encrypt to a public key without a shared secret. OAEP padding is semantically secure.
PBKDF2 / Random IV and salt generation 96-bit IV · 128-bit salt Semantic security Ensures identical plaintext files produce different ciphertext on every encryption.

📤 Sender Workflow — Step by Step

What happens when you click "Encrypt File" on the send page:

H

Step 1 — SHA-512 Hash of Original File

SHA-512

Read all bytes of the file into memory. Pass them through the SHA-512 hash function to produce a 512-bit (64-byte) message digest. This digest acts as a fingerprint — any change to even one bit of the file will produce a completely different hash (avalanche effect). The hex string is stored in the bundle.

// Step 1: Hash original file const fileBuf = await file.arrayBuffer(); const hashBuf = await crypto.subtle.digest("SHA-512", fileBuf); const sha512hex = bufToHex(hashBuf); // → 128-character hex string (512 bits)
G

Step 2 — Generate Fresh AES-256 Session Key

AES-GCM-256

A brand-new 256-bit AES key, a 96-bit IV (Initialization Vector), and a 128-bit salt are generated using the browser's cryptographically secure random number generator. These are unique for every encryption operation — identical files encrypted twice will produce completely different ciphertext.

// Step 2: Generate fresh AES-256 key + random IV + salt const aesKey = await crypto.subtle.generateKey( { name: "AES-GCM", length: 256 }, true, ["encrypt", "decrypt"] ); const iv = crypto.getRandomValues(new Uint8Array(12)); // 96-bit IV const salt = crypto.getRandomValues(new Uint8Array(16)); // 128-bit salt
E

Step 3 — AES-GCM-256 File Encryption

AES-GCM-256

The file bytes are encrypted using AES in Galois/Counter Mode (GCM). GCM is an authenticated encryption mode — it both encrypts the data AND appends a 128-bit authentication tag. If even one byte of the ciphertext is modified, decryption will fail with an authentication error, preventing any tampering from going undetected.

// Step 3: Encrypt file with AES-GCM-256 const ciphertext = await crypto.subtle.encrypt( { name: "AES-GCM", iv }, // GCM appends 128-bit auth tag automatically aesKey, fileBuf ); // ciphertext = encrypted bytes + 16-byte authentication tag const encryptedB64 = bufToB64(ciphertext);
W

Step 4 — RSA-OAEP Wrap the AES Key

RSA-OAEP-2048

The 256-bit (32-byte) AES session key is encrypted using the recipient's RSA-2048 public key with OAEP padding. Only the holder of the corresponding RSA private key can recover the AES key. The plaintext AES key is never stored in the bundle — only the RSA-encrypted version.

// Step 4: Wrap AES key with recipient's RSA-2048 public key const rawAESKey = await crypto.subtle.exportKey("raw", aesKey); const wrappedKey = await crypto.subtle.encrypt( { name: "RSA-OAEP" }, recipientPublicKey, // recipient's 2048-bit RSA public key rawAESKey // 32 bytes of AES key material ); const wrappedKeyB64 = bufToB64(wrappedKey); // wrappedKey = 256-byte RSA ciphertext (RSA-2048 output size)
B

Step 5 — Assemble the Secure Bundle

All components are combined into a self-contained JSON envelope. This bundle can be safely shared over any channel — email, chat, cloud storage. Without the recipient's private key, the contents are unreadable.

{ "version": "SFS-v1.0", "algorithm": "SHA-512 + AES-GCM-256 + RSA-OAEP-2048", "wrappedKeyB64": "<RSA-encrypted AES key, Base64>", ← 256 bytes (RSA-2048 output) "ivB64": "<random 96-bit IV, Base64>", ← 12 bytes "saltB64": "<random 128-bit salt, Base64>", ← 16 bytes "encryptedB64": "<AES-GCM ciphertext, Base64>", ← file + 16-byte auth tag "sha512hex": "<128-char hex SHA-512 of original file>", "fileName": "document.pdf", "fileType": "application/pdf", "fileSize": 1048576, "timestamp": "2026-03-25T10:00:00.000Z" // NOTE: plaintext AES key is NOT stored here }

📥 Receiver Workflow — Step by Step

What happens when you click "Decrypt File" on the receive page:

U

Step 1 — RSA-OAEP Unwrap the AES Key

RSA-OAEP-2048

The recipient's RSA-2048 private key is used to decrypt the wrappedKeyB64 field in the bundle, recovering the original 256-bit AES session key. This is the asymmetric step that makes secure key exchange possible without a pre-shared secret.

// Step 1: Unwrap AES key with RSA private key const rawAESKey = await crypto.subtle.decrypt( { name: "RSA-OAEP" }, recipientPrivateKey, // 2048-bit RSA private key b64ToBuf(bundle.wrappedKeyB64) // RSA-encrypted AES key from bundle ); // rawAESKey = 32 bytes = original AES-256 session key
D

Step 2 — AES-GCM Decrypt the File

AES-GCM-256

The recovered AES key and the IV from the bundle are used to decrypt the encrypted file bytes. AES-GCM automatically verifies the 128-bit authentication tag during decryption — if the ciphertext was modified in any way, decryption throws an error and no output is produced.

// Step 2: Decrypt file with recovered AES key const aesKey = await crypto.subtle.importKey( "raw", rawAESKey, { name: "AES-GCM" }, false, ["decrypt"] ); const decrypted = await crypto.subtle.decrypt( { name: "AES-GCM", iv: b64ToBuf(bundle.ivB64) }, aesKey, b64ToBuf(bundle.encryptedB64) ); // GCM verifies auth tag — throws if ciphertext tampered
V

Step 3 — SHA-512 Integrity Verification

SHA-512

SHA-512 is recomputed over the decrypted file bytes and compared byte-by-byte against the sha512hex field stored in the bundle. If they match, the file is provably identical to what the sender encrypted. Even a single bit change in the file during transit will produce a completely different hash, revealing any tampering.

// Step 3: Recompute SHA-512 and compare const recomputedHash = await crypto.subtle.digest("SHA-512", decrypted); const recomputedHex = bufToHex(recomputedHash); const integrityOk = recomputedHex === bundle.sha512hex; // integrityOk = true → file is authentic and unmodified // integrityOk = false → file was corrupted or tampered
↓

Step 4 — Return Decrypted File to User

If all checks pass, the decrypted bytes are returned as a Blob with the original filename and MIME type, and offered for download. The private key and decrypted bytes are only in memory — they are cleared when the page is closed.

🛡️ Security Properties

PropertyMechanismWhat It Prevents
Confidentiality AES-GCM-256 encryption of file bytes An eavesdropper who intercepts the bundle cannot read the file without the AES key, which is itself protected by RSA
Integrity (file) SHA-512 hash embedded in bundle; verified on decryption Detects any modification to the file bytes after encryption
Integrity (ciphertext) AES-GCM 128-bit authentication tag Detects any modification to the encrypted payload — decryption fails if tampered
Asymmetric Key Exchange AES session key wrapped with RSA-OAEP-2048 Sender and receiver don't need to share a secret in advance. Only the RSA private key can recover the AES key
Semantic Security Fresh random AES key + IV per encryption Identical files produce different ciphertext every time — prevents pattern analysis
Zero-Trust All crypto runs in browser (Web Crypto API) No keys, passwords, or file data are transmitted to any server
